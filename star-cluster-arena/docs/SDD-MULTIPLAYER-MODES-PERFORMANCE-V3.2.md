# 星团大作战：联机平滑、十模式与协议 v2 SDD

- 文档状态：发布候选实现记录；v3.2 双机人工验收待完成
- 目标版本：`3.2.0`
- 日期：2026-08-20
- 适用范围：`star-cluster-arena/` 前后端源码版与 Windows 桌面封装版
- 成品目录：`../star-cluster-arena-desktop/`
- 前置基线：局域网连接稳定性 v3.1 已通过两台 Windows 电脑实测

## 1. 背景与结论

v3.1 已解决局域网发现、防火墙诊断、候选地址回退、玩家退出和双向建房问题。v3.2 处理两个后续问题：

1. 对局移动表现为“走一下、闪现一下”。
2. 联机大厅只能开始自由模式，其他九种单机模式尚未服务器化。

当前卡顿首先是网络同步与渲染采样问题，不是“没有调用电脑性能”。v3.1 基线为服务端 20 Hz 固定模拟、10 Hz 全量快照、客户端只保存前后两帧并在 100 ms 窗口内插值。即使局域网延迟为零，客户端也每 100 ms 才获得一个新位置样本；一旦出现到包抖动、JSON 解析或主线程停顿，插值立即耗尽并钳制到最新状态，视觉上就会跳变。v3.1 本地玩家也等待服务端快照，没有客户端预测，因此房主和客人都会感到输入滞后或位置修正。

“百兆网络”只描述理论吞吐，不保证低延迟、低抖动或没有 Wi-Fi 重传。更重要的是，当前服务端把包含几百个食物点的完整 JSON 快照以 10 Hz 向每个客户端重复广播，出站流量会随客户端数量线性放大。实测表明，食物数据是最主要的重复载荷。

本版本采用以下总方案：

- 保持服务端权威与 20 Hz 固定模拟。
- 动态快照提高到 20 Hz，客户端输入提高到 30 Hz，渲染继续由显示器刷新率驱动。
- 引入服务器时间轴、快照环形缓冲、自适应抖动缓冲和本地移动预测。
- 食物从“每帧全量重复”改为“入局基线 + 增删变化”，动态快照只发送会移动或会变化的实体。
- 引入服务器模式注册表和模式适配器，使十种模式共用模拟核心、各自维护规则与结算状态。
- 联机房间中由房主选择模式和有限规则；配置变化使所有玩家的准备状态失效。
- 协议升级为 `sca-lan-v2`，不与 v1 客户端静默混用。

## 2. 目标与非目标

### 2.1 目标

- 本地玩家移动输入在下一渲染帧内出现视觉反馈。
- 远端玩家在正常家庭局域网中连续移动，不因 20 Hz 网络采样呈现明显阶梯或周期闪现。
- 网络抖动时优先增加少量显示延迟来保持连续性；网络恢复后缓慢降低缓冲，不反复摆动。
- 2～8 名真人可在房间中选择并开始全部十种模式，AI 按模式补位。
- 房间列表、等待房间和对局 HUD 均显示当前模式。
- 规则、随机数、碰撞、积分、队伍、胜负和 AI 全部由房主服务器裁定。
- 20 Hz 紧凑动态快照的带宽低于当前 10 Hz 全量快照，并有可观测的性能预算。
- 两台电脑持续对局 30 分钟无快照队列增长、无房间残留、无不可恢复卡顿。
- 单机十模式和根目录 `ball-arena.html` 不回归、不修改。

### 2.2 非目标

- 本版本不实现公网匹配、NAT 穿透、云中继、账号、排位或反作弊服务。
- 不把 WebSocket 立即替换成 WebRTC/WebTransport。先修复采样、缓冲、预测和载荷；只有指标仍不达标时才评估传输层迁移。
- 不在 v3.2 支持超过 8 名真人。16 连接仅作为协议与带宽压力测试档。
- 不保证联机模式复刻单机宣传中的 100 名真实玩家规模。v3.2 保留每种模式的核心规则，并采用适合 2～8 真人的局域网缩放人数与 AI 补位。
- 不实现主机迁移；房主退出仍关闭房间。
- 不预测吞噬、质量变化或胜负。客户端只预测本地移动，竞争性结果等待服务端确认。

## 3. 研究依据与设计取舍

### 3.1 权威服务器、预测与校正

服务端继续保存唯一真实状态。客户端发送带序号的输入，本地立即预测移动；服务端快照返回已处理输入序号，客户端从权威状态重新应用尚未确认的输入并平滑误差。该流程与 Unreal Engine 官方网络移动中的“保存移动、服务端复现、ACK/校正、重放未确认移动”一致。

远端实体不进行完整本地模拟，而是在服务器时间轴上渲染过去的两个有效状态。Unity 官方 `NetworkTransform` 文档明确建议对非权威实例使用缓冲插值，并指出单纯提高网络 tick 仍不能获得整体平滑，只会增加带宽。

### 3.2 快照频率与插值延迟

Valve Source 官方网络说明给出的成熟基线是约 20 个快照/秒，并用约 100 ms 插值延迟保留两个快照，从而在丢失或延迟一个快照时仍能插值。星团大作战采用相同量级作为初值：20 Hz 动态快照、100 ms 初始渲染延迟。

客户端按 IETF RFC 3550 的一阶估计器计算到包抖动：

```text
D(i-1,i) = (本次到达间隔) - (本次服务器时间戳间隔)
J(i) = J(i-1) + (abs(D(i-1,i)) - J(i-1)) / 16
```

本项目的初始缓冲策略为：

```text
snapshotInterval = 50 ms
targetDelay = clamp(max(2 * snapshotInterval, snapshotInterval + 3 * J), 80 ms, 180 ms)
```

该 `targetDelay` 公式是基于 RFC 抖动估计器的工程初值，并非 RFC 规定；必须通过本项目网络仿真与真机数据调参。缓冲增加采用快路径，降低采用慢路径，避免延迟来回震荡。

### 3.3 WebSocket 保留与背压

浏览器 WebSocket 基于 TCP，消息可靠且有序。优点是现有局域网部署简单；缺点是大消息或丢包重传可能造成队头阻塞。v3.2 不更换传输协议，而是：

- 每个动态快照都是可独立采用的最新状态，服务端积压时不继续排队过期快照。
- 通过标准 `bufferedAmount` 观察未发队列。
- HTTP Upgrade 获得的 TCP socket 显式启用 `setNoDelay(true)`，避免 Nagle 算法用吞吐换延迟。
- 大厅、准备和结算等可靠事件与高频动态状态在消息类型上分开。
- 先使用紧凑 JSON；只有在 16 客户端预算不达标时再引入二进制编码。

## 4. 现状性能证据

以下为同一模拟状态序列化后的 v3.1 基线应用层 JSON 大小，不含 WebSocket、TCP、IP 和 Wi-Fi 开销。v3.1 以 10 Hz 对每个客户端分别广播完整快照。

| 规模 | 完整快照 | 紧凑动态快照 | 缩减比例 | 当前完整快照 10 Hz 总出站 | 目标紧凑快照 20 Hz 总出站 |
|---:|---:|---:|---:|---:|---:|
| 2 客户端 | 31,067 B | 751 B | 97.58% | 4.97 Mbit/s | 0.24 Mbit/s |
| 8 客户端 | 45,919 B | 2,537 B | 94.47% | 29.39 Mbit/s | 3.25 Mbit/s |
| 16 客户端（压力档） | 60,147 B | 4,416 B | 92.66% | 76.99 Mbit/s | 11.30 Mbit/s |

计算方式：

```text
总出站 bit/s = 单快照字节数 * 快照 Hz * 客户端数 * 8
```

2 人采样中食物字段占完整快照约 97.6%。食物绝大多数时间不移动，却被每 100 ms 向每个客户端重复发送，是当前带宽、`JSON.stringify`、`JSON.parse`、垃圾回收和 WebSocket 排队的首要优化对象。

紧凑方案即使把快照频率从 10 Hz 提高到 20 Hz，8 客户端理论应用层总出站仍从 29.39 Mbit/s 降到约 3.25 Mbit/s。这个数量级为平滑插值留出样本，同时显著降低 Wi-Fi 和主线程压力。

### 4.1 v3.2 发布候选实测

`npm.cmd run test:soak` 对每种模式执行 1200 个固定 tick，并同时测量 8 参与者发布档（2 真人模拟输入 + 6 AI）和 16 参与者压力档（8 真人模拟输入 + 8 AI）：

| 档位 | 动态快照 p95 范围 | 动态平均带宽/客户端 | 完整基线最大值 | 模拟 tick p95 范围 |
|---|---:|---:|---:|---:|
| 8 参与者发布档 | 2,901～6,442 B | 45.0～96.2 KiB/s | 37,567 B | 0.024～0.122 ms |
| 16 参与者压力档 | 7,461～15,236 B | 103.5～229.5 KiB/s | 47,550 B | 0.052～0.234 ms |

完整基线每 100 tick（5 秒）发送一次，普通 tick 只发送增量。92 项自动化测试已覆盖十模式真实 HTTP/WebSocket 开局、紧凑编解码、基线/增量修订链、抖动缓冲、本地预测、断线恢复、双实例建房和赛后回房。该数据是本机确定性压力测试，不替代第 15.7 节的两台真机 Wi-Fi、画面流畅度和 30 分钟人工验收。

## 5. 总体架构

```text
房间与模式配置层
  ├─ RoomManager：成员、房主、配置版本、准备状态、房间状态机
  └─ ModeRegistry：十种模式元数据、约束与配置校验

服务端权威模拟层（20 Hz）
  ├─ SimulationCore：移动、分裂、吐球、食物、刺球、碰撞、吞噬
  ├─ PlayerState：输入 ACK、细胞、队伍、生命、分数、连接状态
  ├─ ModeSystems：按模式配置组合生成、tick、胜负和公开状态
  └─ SnapshotEncoderV2：基线、动态快照、模式事件、背压

客户端网络表现层
  ├─ NetworkClock：RTT、服务器时钟偏移、抖动 J
  ├─ SnapshotBuffer：按 tick 排序的环形缓冲
  ├─ RemoteInterpolator：远端实体插值/短时有限外推
  ├─ LocalPredictor：本地移动预测、ACK、重放与平滑校正
  └─ Renderer：requestAnimationFrame 60 Hz 或显示器刷新率
```

### 5.1 复用边界

v3.2 由单个 `AuthoritativeSimulation` 实现共有物理，并根据 `ModeRegistry` 的冻结配置组合模式系统；`ModeSystems` 是职责边界，不要求每个模式复制一个类或模拟器。模式差异只覆盖：

- 模式默认配置与合法范围。
- 参与者/队伍/角色分配。
- 出生、复活、生命和安全区策略。
- 模式专属实体、主动技能和随机事件。
- 计分、排名、胜负与结算。
- 需要同步给所有客户端的 `modeState`。

客户端不能导入单机 `game.js` 后继续独立裁定联机规则。可以抽取纯函数或参数，但最终执行权必须在服务端。

## 6. 房间与比赛状态机

```text
LOBBY → RUNNING → FINISHED → LOBBY
   └──────────────────────────→ CLOSED
```

- `LOBBY`：允许加入、房主改模式/有限规则、玩家准备。
- `RUNNING`：只允许原成员用恢复令牌重连；AI 在断线宽限期接管。
- `FINISHED`：展示权威结果，不再运行物理；保留成员 4 秒后回到 `LOBBY`。
- 回到 `LOBBY` 后保留房间与房主，所有玩家为未准备，可换模式或原模式再来一局。
- `CLOSED`：房主退出、服务关闭或房间过期；释放计时器、模拟和连接。

### 6.1 配置版本与准备状态

房间配置具有递增的 `configVersion`。只有房主可在 `LOBBY` 修改：

```json
{
  "mode": "control",
  "maxPlayers": 8,
  "botCount": 6
}
```

每次有效修改必须原子执行：

1. 校验房主身份与房间仍处于 `LOBBY`。
2. 通过 ModeRegistry 校验模式与 AI 数。
3. `configVersion += 1`。
4. 所有玩家 `ready = false`。
5. 广播新的房间状态。

玩家准备消息必须携带当前 `configVersion`。旧版本准备不得计入开局条件。开始消息也携带 `configVersion`；服务端再次校验最少真人数、所有在线成员准备和模式配置有效后直接进入 `RUNNING`。v3.2 不设置倒计时阶段，以缩短局域网测试往返；后续若加入可取消倒计时，必须单独扩展状态机。

该设计对应成熟大厅系统的通用模型：房间级数据由房主修改，成员只修改自己的准备状态；比赛开始后锁定加入与配置。

## 7. 模式注册表与适配器契约

### 7.1 模式元数据

每个模式在服务器注册：

```js
{
  id,
  version,
  label,
  description,
  minHumans,
  maxHumans,
  recommendedTotalParticipants,
  maxTotalParticipants,
  supportsBots,
  teamPolicy,
  lateJoinPolicy,
  defaultSettings,
  validateSettings
}
```

联机真人上限统一为 8。每种模式可建议不同的总参与者数，AI 最多补 12 个，v3.2 单局总活动星团默认不超过 16。UI 必须显示“真人 X / 8、AI Y、总参与者 Z”，不能把局域网缩放版描述成 100 名真人。

### 7.2 模式规则组合契约

```text
initialize(config, seed)           创建模式状态、分队、角色和专属实体
step(serverTime, dt)               共有物理、模式计分和胜负检查
handleElimination(event)           生命、击杀、复活或出局
setConnected(player, connected)    断线后的 AI 接管与恢复
snapshot(foodMode)                 可复制的模式状态、排名和增量
finishMatch(reason, winner)        幂等权威结算
```

所有模式规则必须满足：

- 固定 seed + 固定输入序列产生可重复结果。
- 不能使用客户端时间作为规则时间。
- 不能把函数、令牌、AI 私有目标或未公开信息放进快照。
- `buildPublicState` 有明确大小预算，禁止把全世界实体复制一遍。
- 模式结束只能发生一次，重复 tick 和重复事件幂等。

## 8. 协议 v2

协议标识升级为：

```text
sca-lan-v2
```

发现协议仍可使用 `SCA-LAN` 发现包格式，但 `protocol` 字段必须为 `sca-lan-v2`。v1 客户端看到 v2 房间时显示“版本不兼容，请更新”，不得尝试解析 v2 快照。

### 8.1 通用字段

所有对局消息包含：

- `matchId`：本局随机 ID，防止上一局迟到消息污染下一局。
- `tick`：服务端递增模拟 tick。
- `serverTime`：服务端单调时钟毫秒值，不使用可跳变的墙上时钟排序。
- `baselineId`：当前世界基线 ID。
- `modeId`、`modeVersion`：规则身份。

### 8.2 客户端到服务器

| 类型 | 关键字段 | 规则 |
|---|---|---|
| `join` | `protocol`, `name`, `hostToken?`, `resumeToken?` | 建立或恢复身份 |
| `room-config-set` | `expectedVersion`, `modeId`, `settings`, `botCount` | 仅房主、仅 LOBBY |
| `ready-set` | `ready`, `configVersion` | 只修改本人状态 |
| `start` | `configVersion` | 仅房主；服务端重新校验 |
| `input-v2` | `seq`, `clientTime`, `dx`, `dy`, `actions[]` | 30 Hz 上限；方向归一化 |
| `resync-request` | `matchId`, `baselineId`, `foodRevision` | 检测状态缺口后请求新基线 |
| `ping` | `seq`, `clientTime` | 时钟偏移和 RTT 样本 |
| `leave` | `matchId?` | 主动离开，幂等 |

动作使用独立 ID，防止重放或重连时重复触发：

```json
{
  "type": "input-v2",
  "seq": 481,
  "clientTime": 18352.4,
  "dx": 0.81,
  "dy": -0.59,
  "actions": [
    { "id": 92, "type": "split" }
  ]
}
```

- 连续移动只保留最新输入。
- `split`、`eject-start`、`eject-stop`、`quick-merge`、`screen-dash` 等离散动作必须白名单校验。
- 服务端按玩家保存最高 `seq` 与已执行动作 ID；重复动作不得执行两次。
- 服务端每秒最多接受 60 条 `input-v2`，正常客户端发送 30 条；超限丢弃而不是阻塞模拟。

### 8.3 服务器到客户端

| 类型 | 关键字段 | 说明 |
|---|---|---|
| `hello` | `protocol`, `serverVersion`, `modeCatalogVersion` | 握手能力 |
| `welcome` | `playerId`, `resumeToken`, `room` | 当前房间全量状态 |
| `room-state` | `configVersion`, `config`, `players` | 事件驱动大厅状态 |
| `countdown` | `matchId`, `endsAtServerTime` | 同步倒计时 |
| `match-start-v2` | `matchId`, `config`, `seed`, `rates`, `baselineId` | 锁定本局规则 |
| `world-baseline` | `world`, `foods`, `staticEntities`, `foodRevision` | 加入、重连或重同步时发送 |
| `snapshot-v2` | `tick`, `serverTime`, `groups`, `ejected`, `foodDelta`, `modeState`, `inputAcks` | 20 Hz 动态状态 |
| `match-event` | `eventId`, `tick`, `event`, `data` | 击杀、复活、技能、提示 |
| `match-finished` | `result`, `ranking`, `returnAtServerTime` | 单次权威结算 |
| `pong` | `seq`, `clientTime`, `serverTime` | RTT/时钟样本 |
| `error` | `code`, `message`, `retryable` | 可显示错误 |

### 8.4 基线与食物增量

`world-baseline` 一次发送当前全部食物和静态实体：

```json
{
  "type": "world-baseline",
  "matchId": "m-...",
  "baselineId": "b-...",
  "tick": 0,
  "foodRevision": 1,
  "world": { "width": 5200, "height": 5200 },
  "foods": [["food-1", 120.4, 811.2, 5.1, 2]],
  "staticEntities": []
}
```

后续快照只携带变化：

```json
{
  "foodDelta": {
    "fromRevision": 18,
    "toRevision": 19,
    "removed": ["food-1"],
    "spawned": [["food-901", 811.0, 164.2, 4.8, 5]]
  }
}
```

- 增删在同一服务端 tick 原子应用。
- 客户端发现 `fromRevision` 不等于本地 revision 时停止应用该增量并发送 `resync-request`。
- 重连始终发送新基线，不依赖断线前的食物集合。
- 刺球、据点和安全区若静止，使用同一“基线 + 事件/增量”原则。
- 动态快照禁止再次包含完整 `foods` 数组。

### 8.5 紧凑动态状态

v2 先使用无空白 JSON 和定长数组降低字段名重复，保持抓包可读性。示意结构：

```json
{
  "type": "snapshot-v2",
  "matchId": "m-...",
  "baselineId": "b-...",
  "tick": 392,
  "serverTime": 19360.0,
  "groups": [
    ["player-id", 5, 182.4, 2, 1, 481, [["cell-id", 201.2, 881.7, 54.0, 112.0, -38.0]]]
  ],
  "ejected": [],
  "foodDelta": null,
  "modeState": {},
  "events": []
}
```

数组下标语义必须在协议模块中集中定义并用编解码测试锁定，业务代码不得散落魔法下标。位置、半径、速度和质量按显示精度量化；初期维持 0.1 世界单位。若 16 客户端压力测试仍超过预算，再在 `sca-lan-v3` 或 v2 协商能力中引入 `ArrayBuffer`，不得不带版本地静默换格式。

## 9. 网络时钟、插值与预测

### 9.1 NetworkClock

客户端每 2 秒发送一次带序号 ping，使用：

```text
rtt = clientReceive - clientSend
offsetSample = serverTime - (clientSend + clientReceive) / 2
```

- 保留最近 20 个样本。
- 优先使用最低 RTT 样本附近的偏移，避免排队延迟污染时钟。
- 对 offset 使用平滑收敛，禁止单次样本使渲染时间跳变。
- 对每个快照用 RFC 3550 公式更新抖动 `J`。
- HUD 开发诊断显示 RTT、J、目标缓冲、实际缓冲和欠载次数；普通玩家只看到简化网络质量。

### 9.2 SnapshotBuffer

- 按 `matchId + tick` 存入最多 64 帧或 3 秒的环形缓冲。
- 丢弃重复 tick；收到新 `matchId` 或 `baselineId` 时清空旧缓冲。
- 渲染时间为 `estimatedServerNow - interpolationDelay`。
- 从缓冲中寻找包围渲染时间的两帧；不使用“最新包到达时间”直接决定 lerp 进度。
- 普通位置和半径线性插值；速度数据稳定后可对位置使用 Hermite 插值，但不能改变权威碰撞结果。
- 缓冲暂时没有未来帧时，最多按权威速度外推 100 ms；之后冻结远端实体并标记欠载，不能无限外推。
- 死亡、复活、传送、安全区阶段切换等带 `discontinuity` 标志的状态直接切换，不做穿越地图式插值。

### 9.3 自适应缓冲

- 初值：100 ms。
- 下限：80 ms；上限：180 ms。
- 检测到欠载或 `J` 快速升高时，每次最多增加 20 ms。
- 连续 10 秒无欠载且 `J` 下降时，每秒最多降低 2 ms。
- 网络恢复后只调整播放时间尺度（建议 0.98～1.02）缓慢回到目标，禁止删帧式瞬移。
- 连续 2 秒无法保持 180 ms 缓冲时显示“网络抖动”，但仍允许重连机制工作。

### 9.4 本地移动预测与校正

本地预测只覆盖方向移动与惯性：

1. 每个渲染帧采样输入并立即推进本地玩家的显示位置。
2. 以 30 Hz 将最新方向和离散动作发给服务端，保存尚未 ACK 的输入队列。
3. 快照返回每名玩家的最高已处理输入 `seq`。
4. 客户端以权威位置/速度为基准，移除已 ACK 输入并重放剩余输入。
5. 小误差在 100～150 ms 内平滑吸收；超过两个当前半径或带 discontinuity 标志时直接校正。

质量、半径、分裂是否成功、吐球产物、吞噬、死亡和技能命中不做权威预测。可以播放按键反馈，但实体结果只能来自服务器。所有校正指标必须记录；不能用超长平滑掩盖规则错误。

## 10. 服务端发送与载荷策略

### 10.1 频率分层

| 数据 | 频率/触发 |
|---|---|
| 服务端模拟 | 固定 20 Hz |
| 客户端方向输入 | 30 Hz，方向未变时可降频但每 250 ms 至少刷新 |
| 玩家细胞与移动实体 | 20 Hz |
| 食物/静态实体 | 入局基线 + 变化事件 |
| 模式关键状态 | 10～20 Hz，按模式需要 |
| 排行榜 | 2 Hz 或排名变化时 |
| 大厅成员与配置 | 事件驱动 |
| ping/pong | 2 秒一次 |

### 10.2 广播与序列化

- 每 tick 构造一次公共动态状态、序列化一次并复用同一不可变 Buffer/字符串广播。
- `inputAcks` 放入公共快照的玩家表，避免为每个客户端重新 stringify 整个世界。
- 每个 WebSocket 发送前检查 `bufferedAmount`：
  - `<= 32 KiB`：正常发送。
  - `> 32 KiB`：跳过本次非关键快照，只保留下一次最新状态。
  - `> 256 KiB` 且持续 2 秒：标记慢客户端并触发可恢复断线，不能拖慢房间循环。
- 关键的房间、结算和基线消息不得被快照跳过策略丢弃，但仍受总消息大小上限保护。
- Upgrade socket 显式 `setNoDelay(true)`。
- v3.2 默认不启用 `permessage-deflate`；其 CPU/内存收益必须另行基准测试后决定。

### 10.3 暂不启用的优化

在 2～8 真人、最多 16 总参与者下，先不引入视野兴趣管理。若未来恢复 40～100 总参与者，再按每个连接的相机范围发送相关实体。官方引擎的 relevancy、dormancy 和 quantization 原则作为扩容方向，但 v3.2 不能用复杂 AOI 延迟十模式交付。

## 11. 联机大厅与模式选择

### 11.1 用户流程

1. 进入“联机模式”。
2. 创建或加入房间。
3. 等待房间中央显示十种模式卡片；只有房主能选择，其他玩家可查看说明。
4. 房主选择模式后出现该模式允许调整的少量设置，如 AI 数、局长或队伍数。
5. 配置变化时所有人的“已准备”自动取消，并显示“房主已更改模式”。
6. 所有人在同一 `configVersion` 下准备。
7. 房主开始，服务端再次校验配置版本并立即锁定模式与成员、进入对局。
8. 对局结束显示结果，随后全员回到原房间，可换模式或再来一局。

### 11.2 房间显示

房间列表卡片至少显示：

- 房间名和房间码。
- 模式名称与图标。
- 等待/对局中状态。
- 真人数/上限、AI 数。
- 协议版本；版本不兼容的房间不可点击。

等待房间显示：房主皇冠、玩家连接/准备状态、模式说明、规则摘要、预计总参与者、开始条件。非房主的模式控件必须为只读，不能只靠前端禁用，服务端也必须拒绝越权配置。

- 模式状态序列化不超过动态快照预算。

## 13. 性能预算与发布门槛

### 13.1 服务端预算

| 指标 | 8 客户端发布线 | 16 客户端压力线 |
|---|---:|---:|
| 固定模拟 | 20 Hz，无永久追帧 | 20 Hz，无崩溃 |
| tick 绝对漂移 p95 / p99 | `<= 5 / 10 ms` | `<= 8 / 20 ms` |
| 单 tick 模拟 + 模式规则 p95 | `<= 10 ms` | `<= 20 ms` |
| 动态快照构造 + 序列化 p95 | `<= 3 ms` | `<= 6 ms` |
| 动态快照 p95 / 硬上限 | `<= 8 / 16 KiB` | `<= 16 / 24 KiB` |
| 应用层总出站平均 | `<= 5 Mbit/s` | `<= 15 Mbit/s` |
| 单客户端平均 | `<= 128 KiB/s` | `<= 256 KiB/s` |
| WebSocket 队列 | 正常为 0；不得持续超过 32 KiB | 不得持续超过 256 KiB |
| Node 事件循环利用率平均 | `< 60%` | `< 80%` |

### 13.2 客户端预算

| 指标 | 合格线 |
|---|---:|
| 本地输入到视觉移动 | `<= 1` 个渲染帧 |
| Canvas 帧率 | 目标 60 FPS；p95 帧耗时 `<= 16.7 ms` |
| 单快照解析 + 入缓冲 p95 | `<= 3 ms` |
| 远端缓冲欠载 | 正常 LAN 10 分钟 `< 0.5%` 渲染帧 |
| 非规则硬跳 | 正常 LAN 10 分钟 `0` 次 |
| 大于 50 ms 主线程长任务 | 30 分钟 `<= 2` 次且不得由快照解析持续触发 |
| 自适应缓冲 | 正常稳定在 80～120 ms；最差不超过 180 ms |
| 本地校正误差 | p95 小于当前最大细胞半径的 25% |

“正常 LAN”测试档定义为 RTT 0～20 ms、抖动 0～8 ms、无持续丢包。物理网络超出该范围时可以显示质量警告，但不得出现内存/队列无限增长。

开发诊断面板和日志至少记录：

- 服务端实际 tick Hz、tick drift p50/p95/p99、追帧次数。
- 模拟、模式逻辑、快照构造、`JSON.stringify` 各自耗时。
- 基线和动态快照字节数、每秒消息数、每秒总出站。
- 每个客户端 `bufferedAmount` 当前值/峰值、跳过快照数、慢客户端断开数。
- 客户端 RTT p50/p95、抖动 J、时钟偏移、缓冲目标/实际值、欠载和外推次数。
- 快照解析耗时、缓冲长度、重复/过期快照数、FPS、长任务数。
- 本地预测 ACK 延迟、校正距离、平滑校正和硬校正次数。
- 当前 `matchId`、`mode`、`configVersion`；不记录 hostToken/resumeToken。

建议提供可导出的单局诊断 JSON，但默认只保存在本机应用数据目录，昵称应脱敏。诊断数据不得进入权威模拟或改变 tick。

## 15. 测试规范

### 15.1 静态与协议测试

- `node --check` 覆盖所有新增 `.js/.mjs`。
- v2 每类消息有合法、缺字段、越界、未知字段和超长输入测试。
- 紧凑数组编解码往返一致；协议索引常量不可重复或漂移。
- v1 客户端加入 v2 房间得到明确 `protocol-mismatch`。
- `matchId`、`baselineId`、`configVersion` 防止旧消息污染。

### 15.2 模拟与模式契约测试

- 共用物理核心继续覆盖移动、分裂、吐球、食物、碰撞、吞噬、死亡。
- 十种模式运行统一契约测试：初始化、固定 seed、tick、序列化与结算。
- 按第 12 节矩阵为每种模式增加专属规则测试。
- 任何数值不得为 `NaN/Infinity`；实体 ID 唯一；实体数量不越上限。
- 单个模式失败不得遗留 interval、socket、事件监听或全局状态。

### 15.3 快照与重同步测试

- 入局基线完整重建当前食物和静态实体。
- 食物 remove/spawn 增量按 revision 原子应用。
- 人为跳过 revision 后客户端发起 resync 并恢复一致。
- 重连获得新基线，旧 baseline 的快照被丢弃。
- 完整状态与“基线 + 全部增量”最终哈希一致。
- 动态快照断言不含完整 `foods`。

### 15.4 预测和插值确定性测试

- 生成固定服务器时间戳与到达时间序列，验证 RFC 抖动估计数值。
- 20 Hz 快照在 60/120/144 Hz 渲染下位置连续、无依赖帧率的速度变化。
- 到包延迟抖动、单次 100 ms 空窗和重复快照不会导致倒退。
- 缓冲增加快、降低慢，并始终位于 80～180 ms。
- 本地输入立即移动；收到 ACK 后只重放未确认输入。
- 死亡/复活/真正传送使用 hard correction，其余误差走平滑校正。

### 15.5 集成与网络劣化测试

使用真实 HTTP/WebSocket 连接和可控消息调度器测试：

| 档位 | RTT | 抖动 | 状态空窗/丢失表现 | 持续时间 | 期望 |
|---|---:|---:|---|---:|---|
| 理想 LAN | 0～5 ms | 0～2 ms | 无 | 10 min | 缓冲欠载 0，非规则硬跳 0 |
| 家庭 Wi-Fi | 20 ms | 8 ms | 每 30 秒延迟 1 帧 | 30 min | 连续移动，预算全部通过 |
| 劣化 Wi-Fi | 60 ms | 20 ms | 每分钟 100 ms 空窗 | 10 min | 缓冲自增，无队列增长 |
| 恢复压力 | 100 ms | 40 ms | 500 ms 空窗后恢复 | 5 min | 显示警告并恢复，不崩溃 |
| 服务端卡顿 | 基准 | 基准 | 每 5 秒注入 80 ms event-loop stall | 5 min | 追帧有上限，不产生时间螺旋 |

WebSocket/TCP 会把真实丢包表现为迟到和队头阻塞，因此测试以“消息到达空窗/突发恢复”为主要注入方式，而不是假装客户端能收到乱序 TCP 消息。

### 15.6 性能与长稳测试

- 用 2、8、16 客户端分别记录完整与紧凑字节数，结果写入测试报告。
- 8 客户端运行 30 分钟，每种模式至少轮换一次。
- 16 客户端运行 10 分钟压力档，不要求正式支持，但必须不崩溃、不泄漏。
- 比较优化前后的服务端 CPU、ELU、堆、GC、出站和客户端 FPS。
- 测试结束后端口、UDP socket、interval、Electron 和浏览器进程全部释放。

### 15.7 两台真机验收

1. 两台电脑安装同一个 v3.2 候选包，确认协议均为 `sca-lan-v2`。
2. A 建房、B 加入，在自由模式连续绕圈和快速反向 5 分钟，录像检查无周期闪现。
3. B 建房、A 加入，重复相同测试，排除房主方向差异。
4. 轮换十种模式；每种至少触发一项专属规则并完成或强制结算。
5. 对局中让客人断网 5 秒再恢复，确认身份、队伍、模式状态和基线恢复。
6. 8 客户端条件无法真机凑齐时，至少 2 台真机 + 6 个自动客户端运行 30 分钟。
7. 导出两端诊断，确认快照、缓冲、校正与带宽预算。

## 16. 实施顺序

## 17. 发布、开源与回滚

### 17.1 发布门槛

- 静态检查、单元、集成、模式矩阵、性能和桌面冒烟全部通过。
- 2 台真机双向建房、重连和十模式验收通过。
- 8 客户端 30 分钟无崩溃、无持续队列、无资源泄漏。
- 实测应用层出站、快照大小和客户端帧耗时满足第 13 节。
- v3.1 安装包/便携包仍可恢复，v3.2 构建成功前不覆盖唯一旧成品。
- `ball-arena.html` 未修改，单机十模式回归通过。

### 17.2 版本兼容

- v3.2 房间只接受 `sca-lan-v2`。
- 局域网列表可显示 v1 房间，但必须禁用加入并提示双方更新到同版。
- 不在同一房间桥接 v1/v2，因为两者快照、时间轴和模式状态语义不同。
- 协议或模式 schema 再变化时递增版本，不能依赖客户端猜测字段。

### 17.3 回滚

- 实施前创建/保留可定位的 v3.1 Git 标签和构建产物校验值。
- v3.2 按阶段提交；协议、平滑、模式框架和各模式迁移分开，便于定位回退。
- 若候选版出现高频断线、规则错判、持续 `bufferedAmount` 增长或数据不一致，停止发布并恢复 v3.1 分发文件，不继续让不同协议客户端混玩。
- 本项目无数据库迁移，回滚不需要转换玩家数据；房间均为内存态，版本切换前关闭旧房间即可。
- 已发布 v3.2 后若必须回滚，发布说明应明确“所有参与者统一回到 v3.1”，并保留 v3.2 诊断文件用于修复。

### 17.4 GitHub 开源流程

目标仓库：<https://github.com/wangzifan396-wzf/mini-browser-games>

只有在本地发布门槛通过后执行外部写入：

1. 审计 `git status`，只纳入本项目文件，不覆盖用户其他游戏的改动。
2. 确认 `.gitignore` 排除 `node_modules/`、日志、用户数据、临时测试和 Electron 中间目录。
3. 检查仓库许可证与第三方依赖许可证；不得提交令牌、证书或代码签名密码。
4. 源码、SDD、README、测试和锁文件进入源码提交；大型安装包/ZIP 优先放 GitHub Release，不直接塞入普通 Git 历史。
5. 使用版本标签 `v3.2.0`，Release 说明列出协议不兼容、局域网要求、十模式范围、测试结果和已知限制。
6. 推送或创建 Release 属于外部状态变更，实际执行前再次确认远端、分支和用户授权。

## 18. 完成定义

以下条件全部满足才可宣告 v3.2 完成：

- 协议升级为 `sca-lan-v2`，基线/增量/动态快照及重同步工作正常。
- 20 Hz 动态快照、服务器时间轴、自适应缓冲和本地移动预测投入使用。
- 2、8、16 客户端数据达到性能预算；与第 4 节基线相比有报告可查。
- 十个模式均由服务器权威模式系统驱动并通过第 12 节自动化验收矩阵。
- 房主可在房间内选模式，配置变更使准备失效，赛后回到原房间。
- 双机实际游玩不再出现稳定复现的“走一下、闪现一下”。
- 断线恢复、主动退出、双向建房和防火墙诊断无 v3.1 回归。
- 自动化测试全部通过，桌面安装版和便携版重新生成并验证。
- 用户确认候选成品无问题后，才进入 GitHub 开源发布步骤。
